## 1 目的与范围

按「集成 / 冒烟 / 回归」三层组织自动化测试，并额外覆盖 AI 能力带来的脚本功能测试与 UI 自动化测试。目标是让每批迭代都有客观的准入门槛和出厂门槛，避免依赖人工点页面判断。

适用范围：`backend/`（Django + DRF）、`frontend/`（Vue 3 + TS）、`scripts/`（运维与门禁脚本）。

不在本计划范围：性能压测、安全渗透、数据库兼容性矩阵（属 I10-T02/T03），本计划只预留接口与数据目录。

## 6 环境与配置要求

| 项 | 要求 | 说明 |

| 测试库权限 | `shop` 账号需 `CREATE`/`DROP`，或本地用 root 跑测试 | 当前本机用 root：`$env:DB_USER="root"; $env:DB_PASSWORD=...` |

## 7 执行门禁与节奏

| 时机 | 命令 | 时长目标 | 失败处理 |
| --- | --- | --- | --- |
| 每批迭代**开场** | `powershell -File scripts/smoke.ps1` | ≤ 3 min | 停止开发，先修环境或回滚 |
| 每次提交前 | `pytest backend/tests/integration -q` | ≤ 2 min | 禁止提交 |
| 前端改动提交前 | `cd frontend; npm run test` | ≤ 1 min | 禁止提交 |
| 每批迭代**收尾** | `powershell -File scripts/test-all.ps1` | ≤ 8 min | 视为未交付，不得登记验收 |
| 发版前 | `test-all.ps1 -Full`（含 concurrency、E2E 全量、覆盖率） | ≤ 20 min | 阻断发版 |

门禁规则：

1. 冒烟失败 → 该批迭代不能开始，不允许「边修边开发」。
2. 集成失败 → 不允许提交；若确属他人遗留，须记录缺陷编号后单独提交修复。
3. 回归失败 → 任务状态只能登记「开发中」，不能登记「AI 已交付」。
4. 三层全绿是登记 `docs/acceptance/**` 中「自动测试和自检证据」字段的前提。

## 11 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 测试库建库权限不足 | 测试无法启动 | 给 `shop` 补 `CREATE` 权限；或本地用 root 并通过环境变量注入 |
| schema 重建慢 | 单轮回归超过 2 分钟 | `--reuse-db`；`transactional_db` 仅用于并发用例 |
| `TestCase` 无法验证行锁 | 并发结论假通过 | 强制使用 `transactional_db`，并在用例中断言超时行为 |
| Playwright chromium 缺失 v1255 | E2E 起不来 | `channel: "chrome"` 复用系统 Chrome |
| E2E 依赖两个 dev server | 启动不稳定 | `webServer` 配置 + 健康检查等待；`test-all.ps1` 统一托管 |
| 三层全量拖慢迭代 | 每批超 30 分钟 | 冒烟优先；集成按迭代增量补；并发与 E2E 放发版前 |
| 覆盖率冲刺与功能开发冲突 | I10 无法达标 | 每批只要求「不降低」，冲刺集中放 I10-T01 |
| 用例与验收清单脱节 | 回归跑绿但仍不合格 | 用例 docstring 必须标注任务 ID；矩阵缺失即门禁失败 |

### 13.3 负向验证暴露的缺陷（需单独立项修复）
