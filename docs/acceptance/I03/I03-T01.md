## 图片校验（本批次新增）

`backend/common/images.py`（Pillow 已是项目依赖，`seed_demo` 生成占位图也用它，未新增第三方包）：

| 检查项 | 规则 | 拒绝时的提示 |
| --- | --- | --- |
| 大小 | `0 < size ≤ 5 MB`（`5 * 1024 * 1024`） | 图片不能超过 5 MB |
| 扩展名白名单 | `.jpg .jpeg .png .webp .gif` | 只支持 JPG / JPEG / PNG / WebP / GIF 格式的图片 |
| **真实解码** | `Image.open()` + `verify()`，异常即拒绝 | 文件内容不是有效图片，已拒绝 |
| 扩展名与格式一致 | JPEG↔jpg/jpeg，PNG↔png，WebP↔webp，GIF↔gif | 文件扩展名与实际图片格式不一致 |
| 单边上限 | ≤ 6000 像素 | 图片单边不能超过 6000 像素 |
| 总像素上限 | ≤ 2400 万（解压炸弹口径） | 图片总像素过大，疑似解压炸弹 |
| 文件指针复位 | 校验后 `seek(0)` | —— 否则写盘会拿到空内容 |
| 地址协议 | `path` 只接受 `/` 开头或 `http(s)://`；拒绝 `javascript:`、`data:`、`//host` | 图片地址需以 / 或 http(s):// 开头 |

为什么不能只看扩展名或 `Content-Type`：两者都由客户端提供，把 `shell.php` 改名成 `a.png` 即可绕过。只有真正解码一次才能确认「这是图片」。

三处生效位置：

1. `ProductImage.image` 字段 `validators=[validate_image_file]` —— Django Admin 表单、DRF 序列化器都会执行
2. `ProductImage.save()` —— 脚本 / shell / 将来的 API 直接写库也拦得住（`full_clean()` 不会被调用，所以要显式校验）
3. `ProductImage.path` 字段校验器 + `save()` 内 `validate_image_path()` —— 防止后台填进 `javascript:` 让前台 `<img :src>` 变成注入点

上传后地址自动写入：文件在 `super().save()` 的 `pre_save` 阶段才落盘、`upload_to="products"` 也在那时拼进名字，因此 `path` 在保存后用 `/` + `image.url` 补齐为 `/media/products/<文件名>`，与 `seed_demo` 使用的 `/media/demo/*.png` 同一约定，前台 `cover_image` 可直接当 `src`。

## 已知问题

1. 图片删除不会连带删除磁盘文件：`ProductImage` 被删或替换后，旧文件仍留在 `media/products/`。清理需要单独的管理命令（未做），当前靠发布前的 `media` 备份与人工清理。
2. 未做图片二次压缩/缩略图：原图直出，5 MB 上限只是拒绝过大的文件，不保证前台加载速度。
3. 图片是同步写入本地磁盘，多实例部署时会不一致；本项目为单机直接部署，符合当前拓扑，若将来横向扩展需换成对象存储。
4. 没有 EXIF 清洗：相机照片可能携带 GPS。若要上公网展示用户上传图，应在 I08（评价配图）前补 `Image.exif_transpose()` 与元数据剥离。
