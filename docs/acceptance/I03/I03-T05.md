## 本批次新增：60 秒 TTL 的时间旅行验证

背景：此前只有「写入时主动失效」的用例（INT-CAT-07），无法证明「如果失效钩子漏了 / 进程刚重启 / 多进程各自持有缓存」，60 秒后数据会自动纠正。验收清单里「失效异常时最迟 60 秒过期」这一条一直缺证据。

实现方式：**不给项目引入 `freezegun`**。它会 patch 全局 `time.time`，影响日志时间戳、`created_at`、JWT 过期判断等一大片无关行为，测试面太宽。本任务的验证目标只有一个——「缓存条目到点后是否被当作不存在」，因此只替换 `django.core.cache.backends.locmem` 模块内的 `time` 引用（`tests/support/cache_timetravel.py`）：

| 工具 | 作用 |
| --- | --- |
| `require_locmem()` | 返回真实的默认缓存后端；非 `LocMemCache` 时跳过。注意 `django.core.cache.cache` 是 `ConnectionProxy`，直接 `isinstance` 永远为 False，必须经 `caches["default"]` 取 |
| `travel(seconds)` | 让 LocMem 的过期比较认为「现在」是 N 秒之后（上下文管理器，退出即还原） |
| `remaining_ttl(cache, key)` | 读出某键剩余寿命。`_expire_info` 的键是 `make_key()` 处理过的（带 `:1:` 版本前缀），业务 key 要先转换，否则永远查不到 |

新增用例：

| 用例 | 断言 |
| --- | --- |
| `INT-CAT-09` | `CATEGORY_CACHE_TTL == 60`（常量被改动即失败）+ 首次请求后该键剩余 TTL 落在 55~60 秒（证明真的写入 60 秒，不是永久、也不是 0） |
| `INT-CAT-10` | 绕过 Admin 直接改库、不做任何失效，**时间旅行 30 秒**后仍返回旧值（证明缓存确实生效，兜底不是「每次都回源」） |
| `INT-CAT-11` | 同上场景，**时间旅行 61 秒**后自动返回新值（兜底生效），且回源后重新写回缓存 |
| `INT-CMS-09` | 横幅缓存 `CACHE_TTL == 60` 且剩余 TTL 55~60 秒 |
| `INT-CMS-10` | 横幅：59 秒仍为旧标题 → 61 秒变新标题 |

## 本批次新增：N+1 查询计数

`INT-CAT-12`：同一分类下先建 3 个商品（各 2 个 SKU + 1 张图），测量一次列表请求的 SQL 条数；再加 9 个（总数 12，4 倍数据量）后重测。断言两次条数**完全相同**，并加绝对上界 `≤ 8`，防止「三次和十二次都是同一个错误写法」这类巧合。

`INT-CAT-13`：单规格商品与五规格商品（带图）的详情页 SQL 条数相同。

## 真机实况

### 1. Redis TTL 与 61 秒真实过期（开发库 + 真实 Redis db1 + 运行中的 dev server）

不依赖时间旅行，真等 61 秒：

```text
PS> python manage.py shell -c "... 清空 key → GET /api/v1/categories/ → 直接改库 → 等 61 秒 → 再 GET ..."
SAMPLE_CATEGORY: digital | 数码影音
FIRST_FETCH_COUNT: 3
REDIS_TTL_AFTER_FETCH: 60 seconds
IMMEDIATE_STILL_CACHED_OLD: True
AFTER_61S_HAS_NEW_NAME: True
REDIS_TTL_AFTER_REFETCH: 60 seconds
RESTORED: 数码影音
```

横幅同理：`BANNERS: 3` / `BANNER_TTL: 60 seconds`。

> 踩坑记录（写进交接文档 §5，避免重犯）：做「把 TTL 改成 None 看测试是否失败」的变异检查后，用 `Copy-Item` 还原文件会带回**更旧的 mtime**，而 Django `StatReloader` 只在 `mtime > 已记录值` 时才重载，于是 dev server 一直跑着变异版本，真机实测出现 `REDIS_TTL: -1`（永不过期）的假象。判定这类现象前先确认服务已重载（touch 文件或重启）。

### 2. SQL 计数（开发库 8 个在架商品）

```text

LIST_SQL_COUNT: 4
DETAIL_HTTP: 200 DETAIL_SQL_COUNT: 3
```

## 已知问题

1. `travel()` 只对 `LocMemCache` 有效（Redis 的过期由服务端判定，客户端改时间无用）。因此 CI 里的时间旅行是「语义等价验证」，Redis 上的真实过期由本文档的 61 秒实测承担，两者不能互相替代。
2. `remaining_ttl()` 读的是 `LocMemCache._expire_info` 内部结构。Django 升级若改动该实现，需要同步调整；已用 `require_locmem()` 在换后端时跳过而非误报。
3. 缓存目前只有「分类列表」与「横幅列表」两处，商品列表/详情完全不走缓存——这是有意的（分页与筛选组合多，命中率低）。若将来加缓存，必须同时补 TTL 与失效用例。
4. 未做缓存击穿保护（同一 key 并发未命中时会有多个请求同时回源）。当前数据量下数据库足以承受，登记为已知限制而非缺陷。
