# 基线管理

版本：1.0｜编制日期：2026-11-15｜状态：已建立，待人工审核

> 本文是「迭代闭环」的实施载体。每次迭代收尾时，在此登记一个基线；新会话、回滚、审计均以基线为准。
> 配套文档：`迭代计划文档.md`（任务状态）、`docs/交接文档.md`（接手详情）、`docs/testing/测试计划.md`（门禁）。

## 1 基线的定义

**基线（baseline）= 一次可复现、可回滚、证据齐全的代码快照。**

一个基线必须同时满足四个条件，缺一不算：

| 条件 | 判定方式 |
| --- | --- |
| 代码已冻结 | 打上 Git 标签，且已推送到远端 |
| 门禁已通过 | 冒烟退出码 0、测试通过、覆盖率不低于上一基线 |
| 状态已登记 | `迭代计划文档.md` 第 15 节与本文基线清单同步更新 |
| 可回滚 | 回滚命令可执行，且写在本文第 6 节 |

只有四处同时更新，才算闭环；只提交代码不打标签，或只打标签不更新文档，都不算基线。

## 2 编号规则

| 项 | 规则 |
| --- | --- |
| 标签格式 | `baseline-NNN`（三位递增，与迭代号解耦） |
| 类型 | annotated tag，必须带说明 |
| 说明内容 | 迭代号 + 覆盖任务 + 门禁结果摘要 |
| 命名理由 | 迭代号可能回退重做，基线号单调递增，永不重用 |

历史遗留标签 `v1.0.0-i01` 保留不改名，在清单中作为 BL-000 归档。

## 4 基线闭合流程

每次迭代收尾按以下顺序执行，任一步失败则本迭代不登记基线。

| 步 | 动作 | 命令 / 产物 | 失败处理 |
| --- | --- | --- | --- |
| 1 | 跑全量门禁 | `pwsh -File scripts/smoke.ps1` | 退出码非 0 则停止，先修问题 |
| 2 | 跑后端测试与覆盖率 | `cd backend && ..\.venv\Scripts\python.exe -m pytest` | 覆盖率低于上一基线则失败 |
| 3 | 更新任务状态 | `迭代计划文档.md` 第 15 节逐任务勾选 | 不得跳过后补 |
| 4 | 更新交接文档 | `docs/交接文档.md` 版本号与变更记录 | 缺陷、缺口须同步 |
| 5 | 登记基线 | 本文 §3 新增一行 | 编号连续，不跳号 |
| 6 | 提交 | `git commit`（代码 + 三份文档同一提交） | 文档与代码必须同提交 |
| 7 | 打标签 | `git tag -a baseline-NNN -m "..."` | 说明含迭代号与门禁摘要 |
| 8 | 推送 | `git push origin main --tags` | 标签未推送视为未闭环 |
| 9 | 验证 | 本文 §5 的启动检查 | 检查不过不得开启下一迭代 |

### 4.1 迭代与基线的关系

```
BL-001（已闭合，当前有效）
   │
   ├── I04 开发（购物车与订单）
   │      └── 收尾：门禁 → 更新计划/交接 → 提交 → 打 baseline-002 → 推送
   │
   ├── I05 开发（模拟支付与状态机）
   │      └── 收尾：baseline-003
   │
   └── … 依次类推，每个迭代一个基线
```

规则：**一个迭代可以对应多个基线（补丁基线），但一个基线只能属于一个迭代。**

## 5 新会话启动指引

关闭当前会话、开启新会话时，按以下步骤恢复上下文。

### 5.1 三份必读文档（顺序不可换）

| 顺序 | 文档 | 读它解决什么 |
| --- | --- | --- |
| 1 | `docs/基线管理.md`（本文） | 我现在站在哪个基线、下一步做什么 |
| 2 | `docs/交接文档.md` | 45 任务状态、5 项缺陷、接手步骤 |
| 3 | `docs/testing/测试计划.md` | 门禁怎么跑、覆盖率目标、待建用例 |

`迭代计划文档.md` 按需查阅，不必全文读（约 300 行，仅在需要任务明细或验收标准时定位到具体章节）。

### 5.2 可直接粘贴给新会话的开场白

```
项目：D:\myProject，GitHub meavia-jing/galaxy，分支 main。
当前基线：baseline-001（提交 6f8cd9a），详见 docs/基线管理.md 第 3 节。

请先读这三份文档再动手：
1. docs/基线管理.md
2. docs/交接文档.md
3. docs/testing/测试计划.md

约束（务必遵守）：
- 单批次工作量不超过 30 分钟，做完汇报。
- 单个文件行数上限见 开发架构文档 5.4 节（Python 400 / Vue 300 / CSS 500 / 任何手写文件 800），
  冒烟 SMK-14 会自动检查。
- 不得由 AI 预填「验收通过」，只能登记「AI 已交付」。
- 提交前必须跑：cd backend && ..\.venv\Scripts\python.exe -m pytest
  和 pwsh -File scripts\smoke.ps1，两者退出码都必须是 0。

下一步待办（按此顺序）：
1. 修复 Redis 故障链：限流器 fail-open、缓存回源、500 纳入信封。
2. 补 B5 地址并发行锁用例（transactional_db）。
3. 补 deploy/ 模板文件，修正 docs/deployment.md 表述。
```

### 5.3 启动前的自检（30 秒）

```powershell
cd D:\myProject
git status -sb                 # 期望 main...origin/main，无未提交改动
git describe --tags            # 期望 baseline-001
pwsh -File scripts\smoke.ps1   # 期望 14/14，退出码 0
```

四项中任一项不符，先查清原因再开发，不要带着脏状态开始。

## 6 回滚到基线

### 6.1 只回滚代码（保留历史，推荐）

```powershell
cd D:\myProject
git log --oneline baseline-001   # 确认目标提交
git revert --no-commit <错误的提交>..HEAD
git commit -m "revert: 回滚到 baseline-001"
```

### 6.2 强回滚到基线（丢弃后续提交，慎用）

```powershell
git reset --hard baseline-001
git push --force-with-lease origin main
```

> 会丢失后续提交且改写远端历史。仅在基线之后的提交全部作废时使用，执行前必须先确认已备份。

### 6.3 数据库回滚

代码回滚不自动回滚数据库。若基线包含迁移变更，需按 `docs/deployment.md` 的发布/回滚章节执行：

```powershell
cd backend
..\.venv\Scripts\python.exe manage.py migrate <app> <上一个迁移编号>
```

生产环境必须先停写、备份，再回滚，并记录丢失的时间区间。

## 7 基线与任务状态的区别

这两个概念经常混淆，必须分清：

| 概念 | 含义 | 谁能变更 |
| --- | --- | --- |
| **基线** | 代码快照 + 门禁证据，客观可验证 | AI 可打标签，但需人工确认 |
| **任务状态** | 单个任务是否交付、是否验收 | 「AI 已交付」由 AI 登记；「验收通过」只能由人工签署 |

关键推论：**基线存在 ≠ 任务验收通过**。BL-001 已打标签，但 45 个任务全部仍是「待审核」，没有任何一个通过人工验收。
